## 開発ルール

## 1. 文書概要

|項目|内容|
|---|---|
|対象システム|LiveCloud|
|作成日|2026-08-19|
|対象|React、TypeScript、Supabase、PWA、設計ドキュメント|

本書は、LiveCloudを安全かつ一貫した形で変更するための実装・検証・公開ルールを定める。新機能、修正、リファクタリングのいずれでも適用する。

## 2. 基本方針

- 既存の利用者データを失わないことを最優先する。
- 型で表現できる不正な状態は、実行時判定だけに頼らずTypeScriptの型で防ぐ。
- 画面、共通UI、データアクセス、型の責務を混在させない。
- 失敗を成功のように扱わず、利用者へ状況を伝え、可能な範囲で作成済みデータを後片付けする。
- 仕様や画面に影響する変更は、実装と同じ変更単位で設計書を更新する。

## 3. 開発環境とコマンド

|目的|コマンド|備考|
|---|---|---|
|依存関係の導入|`npm ci`|`package-lock.json`に従い再現可能な環境を構築する。|
|アプリ開発サーバー|`npm run dev`|Vite開発サーバーを起動する。|
|本番ビルド|`npm run build`|TypeScript型チェック後、ViteとPWAの成果物を生成する。|
|静的解析|`npm run lint`|ESLintを実行する。自動生成されたBlumeファイルが存在する場合は、生成物を対象外にして確認する。|
|設計書サイト起動|`npm run docs:dev`|Blumeの開発サーバーを起動する。|
|設計書サイトビルド|`npm run docs:build`|静的な設計書サイトを生成する。|
|隔離ビルド|`cd docs-site && node ../node_modules/blume/bin/blume.mjs build --isolated`|既存の設計書開発サーバーを停止せずに検証する。|

依存関係を変更した場合は、`package.json` と `package-lock.json` を必ず同時に更新する。

## 4. TypeScript・React実装ルール

### 4.1 型

- `any` は使用しない。外部入力やJSONは `unknown` として受け取り、型ガードで検証する。
- 画面をまたいで使用するデータ型は `src/types/` に定義する。
- コンポーネントのpropsは `type <ComponentName>Props` として明示する。
- DBのスネークケースと画面用のキャメルケースを同一型へ混在させない。変換箇所を明確にする。
- `noUnusedLocals` と `noUnusedParameters` を満たし、未使用のimport・変数・引数を残さない。

### 4.2 コンポーネントと状態

- Reactコンポーネント名とコンポーネントファイル名はPascalCaseを使用する。
- 画面固有のコンポーネントは `src/pages/<画面名>/`、複数画面で使うUIは `src/components/<部品名>/` に置く。
- stateの配列・オブジェクトは破壊的に変更せず、`map`、`filter`、スプレッド構文または関数形式のsetterで更新する。
- 非同期保存処理には二重送信を防ぐ `isSaving` または同等の状態を設ける。
- ルートパラメータや遷移stateが不足する場合は、画面をクラッシュさせず、復帰導線を表示する。
- リスト描画の `key` は、順序変更や削除があり得る場合に安定したIDを使用する。作成直後でIDがない項目は、将来的な並べ替え実装を考慮して一意キーを付与する。

### 4.3 スタイル

- 画面専用スタイルは画面フォルダ内のCSS、共通部品のスタイルは部品フォルダ内のCSS ModulesまたはCSSに置く。
- モバイル幅を基準にし、入力欄・グリッド・画像が狭い画面で重ならないことを確認する。
- 入力欄には背景色だけでなく文字色、カーソル色、プレースホルダー色を明示し、端末のライト／ダーク配色設定でも判読可能にする。
- `date`、`time`などのネイティブ入力はSafari固有の最小幅を考慮し、狭い画面で必要に応じて1列表示へ切り替える。
- 色・余白だけの変更でも、主要なモバイル幅で画面を確認する。

## 5. Supabaseデータ操作ルール

### 5.1 認証・RLS

- DB・Storage操作の前にSupabaseセッションを取得し、セッションがない場合は操作を中止する。
- すべての新規レコードに `user_id: session.user.id` を設定する。
- RLSポリシーは `user_id = auth.uid()` を基本とし、他ユーザーのデータを取得・変更できないことを前提に実装する。
- クライアントへService Role Keyを配置しない。公開可能キーは `VITE_SUPABASE_PUBLISHABLE_KEY` を使用する。

### 5.2 DB・Storageの整合性

- 画像バイナリはDBへ格納せず、Storageへ保存し、DBにはStorageパスだけを保存する。
- 非公開バケットの画像表示には署名付きURLを生成し、署名付きURLをDBやバックアップの永続データへ保存しない。
- 複数段階の作成で失敗した場合は、作成済みレコードとアップロード済みファイルを削除する補償処理を行う。
- 親レコード削除後もStorageオブジェクトは自動削除されないため、関連するStorageパスを取得して削除する。
- 並び順を持つ `setlist_items` と `live_photos` は、`position` を1から連番で保存する。

## 6. 完全バックアップ・復元ルール

- バックアップは `backup.json` と画像ファイルを含むZIP形式（現行バージョン `2.0.0`）とする。
- バックアップJSONは外部入力として扱い、バージョン、必須フィールド、セットリスト種別、画像ファイル参照を検証してから復元する。
- バックアップにユーザーID、既存DB ID、既存Storageパス、署名付きURLを含めない。
- 復元では新しいDB IDとStorageパスを生成する。バックアップ中のIDやパスを再利用しない。
- 置換復元は、新規データの作成が完了してから既存データを削除する。失敗時は新規作成分を後片付けし、既存データを可能な限り保持する。

## 7. PWA・公開ルール

- `vite.config.ts` の `base`、PWAの `start_url`、`scope` はGitHub Pagesの公開パス `/LiveCloud/` と一致させる。
- Service Workerの更新は利用者の入力を失わないよう、更新可能であることを通知し、利用者の操作で適用する。
- 静的アセットの追加時はPWAのprecache対象を確認する。
- `main` ブランチへのpushでGitHub Actionsが `npm ci`、`npm run build`、GitHub Pagesデプロイを実行する。
- GitHub ActionsのSecretsへ `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` を設定する。値をソースコードやドキュメントへ記載しない。

## 9. 変更完了前の確認項目

- [ ] TypeScriptエラーがなく、`npm run build` が成功する。
- [ ] 静的解析を実行し、新規のESLintエラーを増やしていない。
- [ ] 追加・編集・削除・失敗時の画面表示を確認した。
- [ ] モバイル幅で表示崩れ、文字の視認性、入力欄の重なりがない。
- [ ] データ操作でRLS、`user_id`、Storageパス、後片付けを確認した。
- [ ] PWAに影響する変更では、更新通知と最新アセットの取得を確認した。
- [ ] 仕様に影響する場合は関連する設計書を更新した。
- [ ] ドキュメント変更時は隔離ビルドを成功させた。
